Frostbite Engine's EBX Type System

the Frostbite engine EBX asset node structure relies on a slightly convoluted type system reminiscent of object-oriented languages, such as C# in which EA DICE's internal Frostbite tooling appears to be written

Each EBX node has a type which is split into three main parts:
  • the outer type, also known as the category
  • the inner type, also known as the type or base type
  • the type descriptor, in the case of custom data types

of these, outer and inner types are hardcoded into the engine, while the type descriptors are usually loaded from a shared type descriptor table, in many games found in the initfs file

note that this article only describes the type system and not individual types. it also only covers the RIFF-based binary EBX format used in Frostbite 4 (or simply Frostbite, officially). it may or may not apply to older versions, however brief research suggests that the inner/outer type system is largely a Frostbite 4 thing specifically

Built-in Types

the inner and outer types together make up frostbite's built-in types, and are also known as the type and category, depending on who you ask. the latter terminology is more common, as the popular modding tool Frosty Toolsuite uses those terms, while the former was made up by yours truly after getting annoyed at the confusion between type (inner type) and type (the entire type). in fact even the category is more so a type than a category in practice

Outer Types

outer types can be described as modeling a wrapper type taking in an inner type as a generic type parameter. for example, an array of integer values has an outer type of Array and an inner type of Int, and could thus be written as Array<Int>, something likely familiar to anyone who has worked in programming languages such as Java or C# before

as every EBX type is required to have both an inner and outer type, some outer types act as simple wrapper for inner types to specify that the type is free-standing an not in a container such as an array. these appear to include Struct, Enum, and Delegate. Primitive is also used similarly, however it can wrap any of the primitive inner types

Inner Types

inner types describe what kind of value is actually contained, and include the likes of primitives such as integers, strings, or UUIDs. they are the most similar to types as they are known in almost all programming languages

Frostbite considers some unexpected types such as UUIDs and SHA-1 hashes as primitives

while most inner types indicate that a specific type of value is stored, Struct and Inherited are notable special cases. these essentially act as placeholders for a custom type as defined by a type descriptor rather than some fixed value, and contain no data directly of their own. both are functionally the same as far as parsing binary EBX is concerned, however structs have a specific byte alignment which must be accounted for. they are also presumably treated as value types by the engine

Shared Type Descriptor Table

the shared type descriptor table, as mentioned near the beginning of this article, is what actually holds the definitions for a given Frostbite game's custom types, that largely being classes and structs

this table can be roughly split into three parts: the type signature table, the type descriptor table, and the field descriptor table. technically it also contains two or three other tables, however their purposes are unknown, and therefore they will be ignored

Type Signature Table

the type signature table is the simplest of the three main tables, containing a 20-byte structure consisting of an UUID and an integer. the UUID is used to refer to types externally, while the purpose of the integer is unknown. the indexing of this table is also identical to the type descriptor table, wherein for example the signature at index 413 maps to the descriptor at index 413

Type Descriptor Table

the type descriptor table, to which the signature table is essentially a companion, contains the actual definitions for each of a game's custom types in 16-byte structures as follows

the specific bit widths in the type bitfield vary by Frostbite version, however the basic structure remains the same. these ones are used in Need for Speed: Unbound, running a 2021 variant
TypeNameDescription
uint id type ID
uint fieldIndex index of first type field
ushort fieldCount number of type fields
16 bits type
1 bit unknown unknown
4 bits outerType enum index for the outer type
5 bits innerType enum index for the inner type
6 bits flags flags presumably used for EBX property connections
ushort size size of type instances in bytes
ushort alignment byte alignment of type

of these id is simply a replacement for a class name, and if one were to have access to the string table for example from a memory dump of the game, the IDs could be mapped to person-friendly names

for parsing an EBX tree the fieldIndex and fieldCount values are most important. fieldIndex points to an index of the field descriptor table, where the descriptor for the first field of this type can be read, and fieldCountindicates how many field the type has. all fields are in order, so for example if you were to have fieldIndex 612 and fieldCount 11, you would want to read fields at indices 612..622, inclusive

the size and alignment are relatively straightforward, as is the type. in fact, the inner and outer type of type descriptors are needed relatively little in parsing EBX, and the equivalent bitfield in field descriptors is far more important

Field Descriptor Table

the field descriptor table is a table of somewhat similar structures to the type descriptors, describing the aforementioned fields instead of types. in object-oriented programming terms for those familiar, these are essentially declarations for a type's member variables. field descriptors may also refer to both custom and builtin types

the field descriptor structure is as follows

TypeNameDescription
uint id type ID
uint dataOffset offset of field data from previous node
16 bits type
1 bit unknown unknown
4 bits outerType enum index for the outer type
5 bits innerType enum index for the inner type
6 bits flags flags presumably used for EBX property connections
ushort typeIndex index of the field's corresponding type descriptor where applicable

id and type are as described in the type descriptor section, and will not be covered here. of the remaining values, dataOffset is essentially an offset in bytes from the end of the previous node in binary EBX. why this is necessary is beyond me, but so are a lot of other things regarding Frostbite's pecularities

typeIndex on the other hand is simply an index into the type descriptor table, used on fields of a custom type. note that on builtin types it is set to 0xFFFF (65535, or -1 if read as signed), acting as a pseudo-null-pointer, and the inner and outer types are used instead
